# On-device site assistant

A floating "Ask AI" button on every page. Pressing it opens a chat panel. Nothing heavy loads until the visitor agrees.

| Option | Runs on | Download | Engine |
| --- | --- | --- | --- |
| Qwen2.5 0.5B, GPU | WebGPU | about 295 MB | Qwen2.5 0.5B Instruct 4-bit, WebLLM (`vendor/web-llm.min.js`, `worker.js`) |
| Qwen2.5 0.5B, CPU | WebAssembly, no GPU needed | about 429 MB | the same model as GGUF Q4_0, wllama (`vendor/wllama/`) |
| SmolLM2 360M, CPU | WebAssembly, no GPU needed | about 230 MB | SmolLM2-360M-Instruct as GGUF Q4_0, wllama. The lightest option |
| Instant answers | nothing | none | the sentence that answers the question, quoted from the site (`bestAnswer` in `search.js`) |

The panel recommends one of these from the device (`recommend()` in `assistant.js`): a working, non-software WebGPU adapter gets the GPU model; no GPU but a fast single thread (`cpuScore()` above `FAST_CPU`) gets SmolLM2 360M; low-memory devices and slow CPUs get instant answers. The visitor can pick any option, and switch at any time from the header menu, mid-conversation. The history carries over; only one model is kept in memory at once. The last choice and the list of downloaded models are remembered in `localStorage` (`archdev-ai`); the files themselves are in the browser's Cache Storage, and a missing file sends the visitor back to the consent screen instead of downloading silently.

The models are stored by the browser (Cache API / OPFS) and stay until site data is cleared or "Remove downloaded models" is used.
Files come from Hugging Face and GitHub; nothing else leaves the device.

## Files

- `launcher.js`: the only script every page loads (added by `app.js`). Makes the button, loads `assistant.js` on click.
- `assistant.js`: panel, consent and download flow, retrieval, streaming chat, error diagnostics.
- `search.js`: BM25 retrieval, prompt building, markdown rendering. Pure, unit tested.
- `index/*.json`: generated by `node scripts/build-assistant-index.mjs` (also part of `npm run build`). `site.json` holds every page, a compact sitemap and the non-docs text; `docs-<topic>.json` holds one docs topic and is fetched only when relevant.
- `vendor/`: pinned copies of WebLLM 0.2.86 and wllama 3.8.1 with their licences. To upgrade, replace the files and re-test.

## How context works

A 0.5B model has a 4k token window (2k on the CPU tier), so docs are not pasted whole. Every question searches the whole index; the open page and its docs topic score higher, and other topics are fetched on demand. The best chunks go into the prompt together with a compact sitemap.

## Tests

`npm run build:assistant && npm run test:assistant`

## Why CPU-only users get instant answers first

Measured on a Ryzen 5 3500U (single-thread WebAssembly, since multi-thread needs cross-origin isolation, which the embedded docs editors would break), prompts of 400 to 700 tokens:

| Model (GGUF Q4) | First word | Speed | Answers |
| --- | --- | --- | --- |
| SmolLM2 135M (105 MB, not offered) | 25 to 80 s | 4 to 5 tok/s | looped, invented code |
| Gemma 3 270M (253 MB, not offered) | 31 to 67 s | 3 to 4 tok/s | ignored the question, off topic |
| Qwen2.5 0.5B (429 MB) | slower still, not timed | | best quality of the CPU options |

Prompt processing, not model size, dominates. No model small enough to answer in 5 s on such a CPU was good enough, so instant answers are made good instead. SmolLM2 360M was added as an opt-in for fast CPUs and was not timed here.
