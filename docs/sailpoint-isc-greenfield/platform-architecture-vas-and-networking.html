Platform Architecture, VAs and Networking

ISC is SaaS, but anything it governs inside your network is reached through virtual appliances you run. Most connectivity incidents on the program traced back to a network or cluster decision made in the design phase, so this page is about getting those decisions right.

Tenants and region

  • Two tenants: sandbox and production. Build in sandbox, promote to production. They are separate organisations, so credentials, VA registrations and some objects do not travel (see the migration page).
  • Region is a one-time choice. Both tenants sat in the same cloud region. The VA firewall allow-list needs the region-specific service endpoints (object storage, queue, database, container registry) as well as the US-east defaults, so write the region into the network request.
  • Org time zone matters. The tenant has an organisation time zone that governs scheduled aggregation times. Workflow schedules carry their own time zone, and identities carry a work-location time zone. That is three time zones in play. Document each one, because a "run at 10pm local" requirement spans all three.

Virtual appliances and clusters

Principles that held up

  1. One cluster per network boundary and blast radius. Group sources by which network they can reach and by how badly you want a fault to spread. We had an HR cluster, a domain cluster per directory estate, an external-directory cluster in another geography, and two general application clusters.
  2. At least two VAs per cluster. VAs update by taking turns, so a single VA means an outage during every update. The design document said two per cluster; the production listing showed the busiest application cluster with one. It also sat in a warning state, and we never proved the cause. Do not run your biggest cluster on one appliance.
  3. Put a cluster near its targets. Latency between a VA and a database shows up as slow or timing-out aggregations. A region-specific app (a platform reachable only from one geography) justified its own placement.
  4. A source cannot simply be moved between clusters. The cluster decides what the source can reach, so choose before you onboard fifty sources onto it.
  5. Clusters fail together. When several unrelated integrations fail at once, suspect the cluster, not the integrations. Write that into your runbook.
  6. Watch cluster status. Two clusters showed a configuring state with an undefined version string for long periods while sources on them still worked. Learn what normal looks like on your tenant so you can spot a real change.

Network requirements to hand to your network team

The VA only makes outbound calls. Typical requirements:

IQService for Active Directory

Writes to Active Directory (create, move, disable, group changes) go through IQService, a small Windows service. Reads can go direct from the VA. Requirements to plan:

  • A supported Windows Server with.NET Framework 4.5.2 or later and PowerShell 3.0 or later.
  • A service account that is a local administrator on the IQService host and an Account Operator or Domain Admin in AD. This is a high-privilege account; scope it as tightly as your model allows and put it under review.
  • Connectivity from the IQService host to domain controllers on the usual directory ports: LDAP and LDAPS (389, 636), Kerberos (88, 464), AD Web Services (9389), global catalog (3268, 3269), DNS (53), SMB (445) and NetBIOS name and authentication ports.
  • The Microsoft APIs IQService calls choose their own dynamic ports, so a firewall between the host and the domain controllers must be permissive. Put IQService close to the domain controllers.
  • Transport security. Ours was configured without TLS to IQService and with plain LDAP to the domain. Decide on TLS from the start; retrofitting it later means touching every domain setting.

Anything that used to be done by scripts in the legacy tool (mailbox conversion, out-of-office, adding licence groups, hiding from the address list) needs an explicit home in the new design. See the Active Directory page.

Selection principle used in the design: AD connector first, then a purpose-built direct connector, then JDBC or Web Services, then flat file as fallback. Disconnected (ticket-based) fulfilment is the last resort and should be replaced as soon as a direct integration exists.

API access and versions

  • Admin automation uses OAuth 2.0 client credentials against the tenant token endpoint, or personal access tokens. Treat both as production secrets (see the security page).
  • API versions in use were v3, beta and v2025. Newer object families (forms, workflows, launchers) are only on the newest version. Beta endpoints can change shape.
  • You will script against the API for dumps, bulk changes and campaign creation. Give those scripts their own API client with a documented scope, rather than reusing someone's personal token.

Administration and break-glass

  • Configure SSO to the production tenant and test it before go-live; the rollout checklist flagged this as a key task.
  • Create break-glass administrator accounts that do not depend on SSO, and confirm the client's administrators can log in with them.
  • Keep a Config Hub backup schedule running. The tenant had weekly automated backups plus manual full backups, which made it possible to compare and restore configuration.

What SailPoint's documentation adds

Checked against the VA system and network requirements and the tenant connectivity readiness guide in October 2026. Our design matched most of it; these are the details worth adding.

TopicDocumented position
Minimum VA size4 processors, 16 GB memory, 128 GB storage (AWS M5.xlarge, GCP n2-standard-4 or equivalent). The readiness guide quotes a smaller range for local hypervisors and a different Azure size, so trust the requirements page
ClustersAt least one production cluster and one sandbox cluster, and at least two VAs in each, sandbox included. No load balancer is needed
PlacementOne VA per virtual machine host. Keep a local cluster close to its source system. A DMZ deployment is not recommended
UpdatesClusters update by rolling, one VA at a time, which is why one VA means an outage
Network methodsStandard (direct outbound through the firewall, recommended), HTTP proxy, or network tunnel for firewalls that cannot allow domain names. The tunnel is not available in the FedRAMP environment
Reserved rangesA source in 10.255.255.241/28 cannot be routed to from any VA. 172.16.0.0/22 is also unusable with the network tunnel
InspectionVAs can trust a private root CA but reject untrusted certificates, so a TLS-inspecting proxy needs its CA installed
MonitoringThird-party monitoring of the VA is not supported
GeographyVAs cannot be installed in countries with data residency or transmission restrictions, and the page names Russia and China
Tenant namingThe org name is 3 to 13 characters, and sandbox gets an -sb suffix on its URL
AdministratorsName break-glass administrators separately for sandbox and production

The readiness guide also lists who should attend the connectivity kick-off: HR system owners, directory and entitlement source owners, identity architects, network and firewall engineers and an infrastructure lead. Invite the network team before the call, not after.

Actions

  • Write the cluster plan (names, VAs, hosts, networks, which sources go where) before onboarding sources.
  • Get platform-support confirmation in writing for any non-standard VA host.
  • Send the network team the URL, port and region list, and test from the VA with the real tenant.
  • Decide TLS for IQService and LDAP now.
  • Document the three time zones and their owners.
